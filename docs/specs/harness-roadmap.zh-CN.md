# 后续迭代方向：双链文本驱动的 Harness（上下文环境化）

状态：**方向草案 v3｜两轮自审后｜讨论稿，未实现**｜相关：[`context-protocol.zh-CN.md`](context-protocol.zh-CN.md)｜迭代记录见 §9

> 本文件回答一个问题：Agent Deck 的 Harness 下一程往哪走。不定义实现细节（那是 context-protocol 的事），只定方向、价值、依赖与顺序。

---

## 1. 核心判断

1. **瓶颈已经从"取不到"变成"取不准、取不多"。** 现有 `resolveDelegationContext` 只能注入最多 3 篇笔记、每篇 12 行、600 字，且把 frontmatter 剥掉。这是"无工具 LLM 时代"的做法，而 agent 的 cwd 本来就在库里、能自己读文件。
2. **上下文不进复利。** 一次派发读到的所有东西在回写时全部蒸发，下次重新猜。所以库越大、笔记越多，派发质量并不随之提高。
3. **资产已经够，缺的是一个契约。** 大纲祖先链、双链解析、语义块号、dream 记忆的三态、9 家 agent 派发、Bases 视图——都已存在。缺的是把它们按同一个"引用—读取—回写"契约串起来。
4. **与 RAG 的分野必须明确：结构优先。** 用户手工标注的结构（缩进层级、列表序号、块引用、`domain`/`father`/`type`）是**人做过判断的注意力痕迹**，信噪比高于 embedding 相似度。向量/词法检索只做"我不知道它在哪"时的兜底，不做主路径。

外部参照：Notion 之所以是当下最好的"上下文托管端"，靠的是「块结构 / Markdown / 向量」三层镜像秒级同步 + 一个能手工修改的界面 + 跨 agent 的 MCP 入口。我们缺的只有后两项的"统一入口"，其余是已有资产。反面教训同样清楚：Notion 收窄 AI 额度、退回"上下文托管端"，说明**不该把模型能力长在自己身上**。

### 1.1 前置承诺：用户继续在 Obsidian 里写日记

本方向**不改变写作方式**。日记、随手记、概念笔记照旧用 Obsidian 原生语法写，Harness 只在**读取侧**做增益。唯一要求改变书写的只有 D5 证据链的 L2 档，而且它可选、有止损线、可回退（§5）。

| 语法 | 我们的处理 | 要求用户改动 |
|---|---|---|
| 双链 `[[笔记]]`、`[[笔记\|别名]]` | 名字解析后固化为路径，回写时还原原写法 | 否 |
| 定点 `[[笔记#^块号]]` | 硬锚点 + 内容 hash 校验 | 否 |
| 章节 `[[笔记#标题]]` | 取该标题到下一个同级标题之前 | 否 |
| 嵌入 `![[…]]` | 计入上下文 | 否 |
| 列表缩进 | 层级唯一依据（Tab / 空格都认） | 否 |
| 列表符号 | 只区分**有序 / 无序**，不取"第几项"（见下） | 否 |
| 标题层级 | 作为主题锚点参与邻居描述 | 否 |
| frontmatter 属性 | 只读映射到 OKF 子集（§4 of context-protocol） | 否 |
| 脚注 `[^id]` | 证据链载体，仅 L2 建议使用 | **是，但可选** |
| 注释 `%%…%%` | 解析时剥离，不作证据来源 | 否 |
| 标注块 `> [!note]` | 标为 callout，不参与大纲层级 | 否 |

**有序列表的技术限制（红线）**：Obsidian 会把有序列表按渲染顺序自动编号，源文本可能是 `1.` `1.` `1.` 或全部被改写。所以"第几项"**不能当作绝对位置或顺序数据**，顺序只能由行位置表达。Agent 侧只能知道"这是一个有序列表"，不能知道"这是第 3 步"。

### 2.2 Q6 修正：Bases 装不下现在这份记忆

原 Q6 写的是"Bases 表或插件内表格"，实际做不到。Bases 的三条硬限制：**行只能是文件**、**只读**、**没有按钮列**。而当前记忆是"一个文件里的 33 条列表项"，在 Bases 里连一行都看不到。

| 路径 | 存储形态 | Base 能用吗 | 勾/叉能用吗 | 迁移成本 |
|---|---|---|---|---|
| **A 一文一条** | 每条记忆一个 `.md` | ✅ 行即记忆 | ❌ 仍需插件承载 | 中（33 条 + dream 写入路径 + `states` 迁移） |
| **B 插件自渲染表格** | 保持单文件列表 | ❌ 用不上 Base | ✅ 插件里做按钮 | 低（不动存储） |
| **C 双写镜像** | 单文件为真相 + 镜像文件给 Base 读 | ✅ | ❌ | 低，但**两份真相**会漂移，不推荐 |

结论三条：① **想要 Base，就必须一文一条，没有第二种办法**；② **Base 天生不能承载勾/叉**，写操作只能靠插件命令或视图；③ C 方案看似省事，但镜像一旦与真相不一致，"这条记忆到底算不算数"就没有唯一答案了。

## 3. 逐条展开

每条固定四个视角：**价值**（为什么值得）、**现状代价**（不做的话现在具体损失什么）、**作用**（做成什么样）、**最小切片**（20% 版本，用来验证方向而不是完工）。

### D1 锚点引用协议
- **价值**：没有它，运行时环境就是"每次都猜位置"。行号会漂移，块号不会，但块号可以缺失、可以重复。
- **现状代价**：`job.line` 是行号主键，笔记一改行号就错位；块引用找不到时现行策略是"宁可不注入、直接跳过"，于是引用越多漏得越多，且**没有任何提示**。
- **作用**：内部 `ref = {target, subpath, anchor:{kind, hash}}`；有块号走硬锚点，无块号用「标题路径 + 内容指纹」做软锚点；hash 只存机器侧，不写进笔记；漂移时明确报错，**绝不拿文件开头冒充**。
- **最小切片**：只在派发时把目标块的锚点（`^id`，无则指纹）+ hash 写进 job，回读时校验一次。不做图遍历、不改既有注入。
- **验收**：50 个真实块引用 hard 命中 100%；块被删/移动/改名/重复 id 四类场景都报漂移；单测可覆盖。

### D2 入口地图注入
- **价值**：现在是注入即上限。改成"入口地图 + 指针"后，覆盖从 3 篇变 N 篇，token 从 ~1800 降到 ~300。
- **现状代价**：第 4 篇双链起**静默消失**（无省略提示）；frontmatter 被 `frontmatterEnd` 剥掉，agent 因此不知道笔记是什么类型、属于哪个领域、有没有被验证过。
- **作用**：固定六段（块原文 / 祖先链 / 属性摘要 / 邻居清单 / 证据清单 / 工具说明），各自有上限；超预算从证据段开始裁，**任何裁剪都要写省略声明**。
- **最小切片**：现有 3 篇内联**保持不动**，只新增"第 4 篇起的指针清单"（路径 + 一行 `def`）。先验证"给了指针，agent 会不会真去读"这个前提。
- **验收**：真实派发注入 ≤ 800 字；裁剪必含省略声明；单测断言段序与上限；3 个真实任务对比新旧 prompt。

### D3 运行时工具层
- **价值**：把上下文从"派发时的一次押注"变成"运行时可查询"，也是未来客户端唯一需要稳定的接口面。
- **现状代价**：agent 的 cwd 本来就在库里，但没人告诉它读什么；派发后不可追问，问错了只能重发一次。
- **作用**：五个动词，签名先定、形态可插拔（插件命令 / CLI / MCP）。`related` 每条必须带 `why`，**不返回分数**。
- **最小切片**：只出 `read(ref)` 一个动词，CLI 形态，最快验证"agent 会不会用它"。
- **验收**：CLI 五动词跑通；一个真实 agent 在无内联摘要情况下完成任务且至少调用一次 `read()`；签名冻结进 spec。

### D4 记忆库化 + 四类纠正
- **价值**：dream 现在只产出"给 Telegram 陪伴档案用"的单文件记忆，派发完全不用。改成库之后，纠正动作成为数据质量来源。
- **现状代价**：33 条记忆挤在一个文件里，纠正只能手改正文里的 `状态：有效` 字符串；四类语义被压成一套状态机（偏好变化被错误地记为"已被替代"）；`settings.dream.states.processed` 一旦丢，14 天日志会被重新抽取一遍，产生重复记忆。
- **作用**：一文一条（`type` = 事实/偏好/待验证规律/项目经验），四类纠正语义分开：事实用 `supersedes`、偏好用 `valid_from`/`valid_until` 时间线、规律用 `verdict`、经验用 `applies_to`；目录配 `index.md` + `log.md`。
- **最小切片**：**只读视图**——解析现有单文件，生成一个按类型/状态分组的 Bases 表，完全不动存储。先让"纠正"这件事在界面上发生一次。
- **验收**：33 条无损迁移且逐条 diff 可审；已拒绝的不再重生；Bases 视图可按 `type`/`status` 过滤；四类纠正各有单测。**唯一会动历史数据的路线**，动手前先备份 `data.json` 与记忆文件，见 §5 回滚步骤。

### D5 证据链
- **价值**：`[[X]]` 从"提到 X"变成"这句源自 X 某处"，这是 agent 敢与你唱反调的前提。
- **现状代价**：双链只能提供"这两篇相关"；dream 的归因是散文（"来源：…（第 26—26 行）；原文：…"），机器查不了；一旦改写文档，位置索引会静默错配。
- **作用**：Obsidian 原生脚注做载体，`sources[].id` 作稳定键；注入时随包给摘录，核验复用现有 `matchVerbatimQuote`；分 L0/L1/L2 三档，不要求日记挂脚注。
- **最小切片**：不做写作规范改变，先写"从已有 `[[X]]` 反推 `sources`"的推导器，让现有 5486 篇零改动即可用。**推导出的条目必须标 `derived: backlink` 并降置信**，不得与手写 `sources` 同等对待——否则等于把"两篇相关"伪装成"这句源自那里"，比不做更糟。
- **验收**：能取回"句子 → `sources` → 具体块"三层；核验失败时 agent 必须标"无法核实"；L2 在示例笔记上验证。

### D6 结构图与关联
- **价值**：替代"关联度分数"。分数难验证，算错的代价是**安静地丢掉正确上下文**，比不注入更糟。
- **现状代价**：`father`（21 篇）与 `sons`（43 篇）不互反，回指一致 **0** 个，从哪个方向进来得到不同邻居；关联没有 `why`，错了也看不出错在哪。
- **作用**：`father` 为唯一声明源；`sons` 只读推导；排序按「显式结构边 > 共享 `sources` > 共同邻居 > `usage_count`」，每条给 `why`。
- **最小切片**：只做推导视图 + 差异报告，**不改库、不进派发**。
- **验收**：`related()` 8 条全部带 `kind` + `why`；同输入可复现；产出差异报告。

### D7 回写闭环
- **价值**：唯一能让上下文随使用变好的机制；也是 dreaming 的高质量输入（从"扫日记"升级为"扫结论 + 证据"）。
- **现状代价**：一次派发后除 🔗 与一行结论外不留痕迹；"读了哪几个文件"完全不记录；dream 只能从日记正文重抽，把已经正确的结论再猜一遍。
- **作用**：结论块带 `<!-- ad-attest: {…} -->`（必须能被 `stripInternalIdentifiers` 剥掉）；目录 `log.md` 追加变更；job 记录这次读过哪些文件。
- **最小切片**：只做 job 侧"读过什么"的记录（不改写任何笔记内容），先让下一次派发能知道上次的读取范围。
- **验收**：一次派发后 `log.md` 出现 Update 行；`ad-attest` 不出现在任何 prompt（用现有剥除逻辑断言）；结论带 sources 时可反查到块。

### D8 可重放 + 缺口检测
- **价值**：可重放解决"事后无法解释 AI 判断"；缺口检测反过来帮用户写笔记（现状已有 8 个断链子项）。
- **现状代价**：事后无法回答"它当时看到的是哪个版本"；8 个断链要人工撞见。
- **作用**：job 序列化注入清单 + 各自 hash；派发前扫断链与未写概念并提示，**不阻塞派发**。
- **最小切片**：先只做注入清单快照（纯记录，零 UI），缺口检测后置。
- **验收**：任意历史 job 能还原当时注入内容与 hash；断链报告出现在派发前。
- **注意**：这一条其实含两件依赖不同的事。**缺口检测零依赖**（只扫库里的断链与未写概念），可以立刻做，是 M0.5 快赢之一；**可重放**才依赖 D1、D2。排期时必须拆开，别当成一件事。

### D9 解耦与独立客户端
- **价值**：用户明确会做独立客户端；现在留缝成本近零，以后补成本巨大。
- **现状代价**：派发链直接依赖 `readNote` 与 `getFirstLinkpathDest`，散在 [harness.js](../../src/harness.js) 的多个函数里；迁客户端要重写整条派发链。
- **作用**：全部内容获取收敛到 `resolveTarget` / `readConcept` 两个接口；格式定义不依赖 Obsidian API；`outline.js` 等纯函数在 Node 下可跑。
- **最小切片**：把"取内容"抽成两个函数的薄封装（**行为不变**），并加一条架构测试卡住越界。
- **验收**：新增测试断言 harness 只经这两个接口取内容；独立 CLI 能读同一份库。

> D9 与 D3 有重叠：两者的接口是同一个东西。**D9 是 D3 的副产品**，不作为独立工期排；只在 D3 落地时把签名顺手冻结成不依赖 Obsidian 的形状。

### D10 库级画像（全库提炼，字段式）

- **价值**：AI 缺的不是"更多上下文"，是**"关于你的先验"**。dream 只看近 14 天日志，得到的是"最近发生了什么"；没有任何地方回答"这个人是谁、长期在意什么"。这个先验只有库级扫描能给。
- **现状代价**：5486 篇笔记只能靠一次次派发现读；职业、长期偏好、在意什么这类信息每次都要用户重新交代，或由 agent 猜（猜错就污染语气）。
- **作用**：三层分开做、分开存、分条件注入（见下表），每条画像字段带来源与状态，用户在 Base 视图里逐条审视、勾/叉/改。
- **字段契约**：`field` / `value` / `status`（`proposed` / `confirmed` / `rejected`）/ `sources` / `generated` / `verified` / `reviewed_at`；完整定义见 [`context-protocol.zh-CN.md`](context-protocol.zh-CN.md) §10.2。
- **最小切片**：只做 L2——纯统计、零模型、输出一份领域地图报告。它同时验证"统计口径对不对"。
- **验收**：L2 口径可复现（同库同结果）；L1 每条画像都能追到原文摘录；勾/叉/编辑之后下一次注入立即生效。

**三层必须分开，因为成本差两个数量级**

| 层 | 内容 | 数据来源 | 要模型 | 更新 | 成本 | 注入条件 |
|---|---|---|---|---|---|---|
| **L1 稳定画像** | 职业、身份、长期偏好、在意什么 | 全库**抽样**（核心笔记 frontmatter + 首段） | 要（一次性） | 季度 | 几万 token/次 | 仅写作 / 选题 / 复盘 / 规划 |
| **L2 领域地图** | 双链最密的概念与领域 | 纯图统计 | **不要** | 每次派生 | ≈0 | 仅选题 / 写文章 / 整理概念 |
| **L3 当下关注** | 最近在写什么、想什么 | 近 14–30 天 | 要（dream 已在做） | 每天 | 小 | 每次派发 |

**L2 的统计口径（关键，否则会得到"谁被提到最多"而不是"在意什么"）**

| 口径 | 做法 | 排除的假信号 |
|---|---|---|
| 只算概念类笔记之间的边 | 排除日记、流水、归档 | 日记里天天提某人不等于在意 |
| 跨笔记类型分布 | 被多少篇**不同类型**笔记引用 | 被一篇日记引用 30 次 |
| 跨时间稳定性 | 连续 N 个月都被引用 | 一时兴起 |
| 共同邻居 | 与当前任务双链目标共享的邻居数 | 全局流行度 |

**为什么画像不该无条件注入**：让 agent"改这个函数"时塞进"你是一个关注自反性的写作者"是纯噪音，还会污染语气（commit message 开始抒情）。必须按任务类型触发，L3 例外——它短且真的相关。

**隐私与成本（前置条件，不是优化项）**：L1 会把几百篇笔记的摘要发给云端模型。跑之前必须明确告知"这次读多少篇、约多少字、发给哪个模型"，支持按文件夹排除与 `private` 标记，且做成**分批 + 可中断 + 可续跑**。

**画像字段怎么"点勾/点叉"**：Base 只能筛选与展示（`status == "proposed"` 即待审），**真正的勾/叉必须由插件承载**——要么命令（选中文件 → 确认/拒绝），要么一个审阅视图（列表 + 按钮，复用现有卡片/表格渲染能力）。两种都能写回 frontmatter，不需要新格式。

## 4. 阶段与顺序

| 阶段 | 包含 | 用户能感知到什么 | 前置条件 |
|---|---|---|---|
| **M0 地基** | D1（及切片 Q7） | 无——纯防错（改笔记后不再读到错位置） | — |
| **M0.5 快赢** | Q1–Q5 | 上下文变全、能看到 34 个待写概念、记忆开始参与派发 | 无，可与 M0 并行 |
| **M1 能读准** | D2 剩余 + D5 | token 下降、注入更准、能追到出处 | M0 |
| **M2 能查能记** | D3 + D4 + D6 + Q6 | 可追问、记忆可维护、关联可解释 | M1 |
| **M3 闭环与平台** | D7 + D9 | 结论带证据回库、迁客户端零重写 | M2 |

**M0.5 为什么不能被 M0 吸收**：D1 是零感知的基础设施，D4 只读视图和 D8 缺口检测则是一两天内能看见结果的东西（断链清单：8 个 `sons` 断链 + 26 个 `domain` 未解析，合计 34 条待写概念）。**单人项目真正的死因是半年没看见效果，不是技术选错**，所以快赢不是可选项。

> 不建议把 D3 排到 M1：它依赖 D1，且只有"内联摘要已经不够用"之后才有必要性。先让用户感到"上下文太少了"，再给他读文件的能力。

## 5. 风险、退出条件与回滚

风险分两类，**行为风险的概率远高于技术风险**，但工程惯例只给技术风险留位置。

| 类型 | 涉及 | 具体风险 | 退出条件（止损线） |
|---|---|---|---|
| **行为** | **D5 证据链** | 要求用户改变写作习惯（写脚注）→ 用了两周就放弃 | 若 4 周内新写的 L2 笔记 < 5 篇，退回"自动从双链推导 `sources`（标 `derived: backlink`，低置信）"，不再要求手写 |
| **行为** | **D3 工具层** | agent 不主动调用工具，仍只吃 prompt | 若指针生效率连续 3 个月 < 10%，说明 agent 不配合，退回"内联摘要 + 更大预算"，工具层降级为人工查询 |
| 技术 | D4 迁移 | 唯一会动历史数据的路线 | 迁移前**必须**备份 `data.json` 与 `Agent Deck/长期记忆.md`；回滚 = 恢复两个文件 + 回退 dream 写入路径 |
| 技术 | D6 `sons` 语义 | 只读推导若与手写字段冲突，用户可能误以为笔记被改 | 推导视图永不写入原笔记；差异只输出报告 |
| 技术 | D7 回写 | 新注释格式若漏剥，污染 prompt | `ad-attest` 未通过剥除断言即视为未完成，不得合入 |
| **行为** | **D10 画像** | 画像一旦错，会污染**每一次**派发（记忆注入是局部，画像是全局） | 每条画像必须有来源摘录、`status: proposed` 起步、默认不注入；连续两次抽检发现画像与实际不符就整体停用 |
| 技术 | D10 全库扫描 | 把几百篇摘要发给云端模型 | 跑前必须显示篇数/字数/目标模型；支持目录排除与 `private`；分批可中断 |
| 技术 | D4→D10 依赖 | 画像字段与记忆字段共用同一套契约，一边改字段另一边跟着坏 | 字段契约先冻结在 context-protocol §10，再实现任何一侧 |

**全局止损**：如果 M0.5 的两个快赢做完、用户自己连续两周没有使用它们，说明方向判断错了（不是实现错了），应当停止后续阶段、重新讨论，而不是继续投入 M1。

## 6. 判据：怎么算这条路走对了

功能验收（上面每条写的"验收"）只证明**做出来了**，不证明**有用**。以下八条是效果判据，**每一条都必须能在不加新 UI 的前提下采集**，否则不会被跟踪，也就等于不存在。

| 判据 | 采集方式 | 目标 | 支撑的方向 |
|---|---|---|---|
| 注入体积 | prompt 长度断言 | 单次 ≤ 800 字（现状约 1800） | D2 |
| 指针生效 | 抽检 20 次派发，看 agent 回复或工具调用里是否出现注入的路径 | ≥ 40% | D2、D3 |
| 漂移捕获 | 派发后故意移动目标块，再重读 | 100% 报漂移，0 次静默读错 | D1 |
| 记忆在用 | 每周被人工确认 / 修正 / 拒绝的条目数 | ≥ 1（看趋势，不看绝对值） | D4 |
| 纠正不复发 | 同一 `memoryId` 被拒绝后是否再生成 | 0 次 | D4 |
| 可重放 | 回放任意历史 job | 1 秒内还原注入清单 | D8 |
| 可解释 | 随机抽 `related()` 结果自查 | 每条都能说清"为什么带它进来" | D6 |
| 回写留痕 | 派发后 job 里"读过哪些文件"非空的比例 | ≥ 80% | D7 |

第一条和第三条可以自动化，应当进 `npm test`；其余是人工抽检，**频率比精度重要**——抽检不做的判据等于没有。

**刻意不进主表的指标**：「上下文复利」（隔两周同类任务的命中率是否上升）。它无法在"什么算同类任务"上取得客观定义，写进主表只会变成装饰。要做就单独立一个实验记录，不当作验收门槛。

## 7. 红线与反面清单

**红线（与既有不变式一致）**

1. 笔记正文只写 Obsidian 原生语法；自定义引用只活在机器侧。
2. 不静默丢上下文：任何裁剪/降级都必须声明。
3. 不存关联分数，只存信号；每条关联可解释。
4. 软锚点找不到时明确报漂移。
5. 内部标识只占 `ad-` 命名空间且必须可被剥离。
6. 不新增"必须填"的字段；缺字段不得拒绝已有笔记。
7. 缺数据不估算（沿用现有口径）。

**明确不做**

1. 不在插件内内置主对话（All in One AI）——模型能力交给 9 家 agent。
2. 不把向量检索当主路径。
3. 不追求全库 OKF 合规（日记保持 L0）。
4. 不自造 Markdown 语法。
5. 不在公共层为单个 agent 特判。

## 9. 迭代记录

### v1 → v2（结构审计）

| 问题 | 改法 |
|---|---|
| 按"方向"组织，不按"能感知到什么"组织 | 每条补 **现状代价**，把"不做会损失什么"写具体 |
| 复杂度写了四维却没用 | 总览表改为「触及文件 / 改笔记契约 / 需数据迁移 / 验证方式」四格，并点出**只有 D4 要迁数据、只有 D4/D6/D7 改契约** |
| 缺最小可验证切片 | 每条补 **20% 版本**，用来验证方向而不是完工 |
| "验收"只证明做出来了 | 新增 §6 判据：八条**效果**判据，且必须能在不加 UI 的前提下采集 |
| D3 与 D9 接口重叠 | 明确 **D9 是 D3 的副产品**，不单独排工期 |

### v2 → v3（执行审计）

| 问题 | 改法 |
|---|---|
| D5 的最小切片有自欺风险：反推的 `sources` 无置信信息却与手写同等对待 | 强制标 `derived: backlink` 并降置信，"把弱信号伪装成强信号比不做更糟" |
| 没有退出条件，三条改契约的路线做砸了无法回退 | 新增 §5 风险与退出条件表，含 D4 备份/回滚、D7 剥除断言、全局止损线 |
| 把行为风险当技术风险排 | §5 显式区分两类，指出**行为风险概率更高**（D5 改写作习惯、D3 靠 agent 自觉调工具） |
| 顺序全是基础设施，半年看不到效果 | 新增 **M0.5 快赢**（缺口检测 + 记忆只读视图，一两天量级，零依赖） |
| 「上下文复利」判据不可测 | 从主表移除，单列"刻意不进主表"，换入可测的「回写留痕」 |
| D4 是唯一动历史数据的路线，却没写备份回滚 | 补入 §5，并在 D4 验收处标注 |

### 定稿时发现的自身矛盾

总览表原写 D8 依赖 D1、D2，但 §4 又把缺口检测列为"不依赖 D1 的快赢"。实际这是两件事：**缺口检测零依赖**（只扫断链），**可重放依赖 D1/D2**。已在总览表与 D8 条目内拆开注明。

## 10. 覆盖不足与遗漏

讨论里没被前面九条覆盖、但会真实咬人的地方：

| # | 遗漏点 | 影响 | 归属 | 建议 |
|---|---|---|---|---|
| G1 | **9 家 agent 能力不等**：有的能读文件（Claude Code / Codex / DSH / OpenCode / Qoder），有的只有桌面或终端交接 | 指针策略对读不了文件的 agent 完全无效 | D2、D3 | 按 `getAgentCapability` 降级：能读给指针，不能读退回内联并注明"已满额" |
| G2 | **外发隐私**：注入内容会随 prompt 发给云端模型 | 私密笔记可能被外发 | D2 前置 | 加"不注入"标记（文件夹级默认排除 / `private: true`），注入前过滤 |
| G3 | **解析失败静默吞错**：`harness.js` 多处空 `catch {}`（如 `/* unreadable linked note */`） | "上下文为什么少了"永远查不到 | Q3 同类 | 加计数与一次可见提示；宁可报"1 篇读取失败"也不要无声跳过 |
| G4 | **编辑器未保存状态**：`readNote` 读磁盘，可能落后于编辑器缓冲 | 刚改完就派发会读到旧内容 | Q7 | 取内容优先走 `cachedRead` + 变更校验；必要时先 flush |
| G5 | **注入 token 没进成本口径**：`usage.json` 只统计会话 token | 无法证明 D2 真的省了钱 | 判据 | 在 job 里记注入字数，与 usage 并列展示 |
| G6 | **内部状态关键词进上下文**：任务行前缀 `DOING` / `🤖` / `❓` 会原样进 prompt | 噪音，且暴露内部标记 | D2 | 扩展 `stripInternalIdentifiers` 的剥离范围（仅派发侧） |
| G7 | **记忆只增不减**：33 条已接近 `activeMemory` 的 6000 字上限 | 到 100 条就装不下 | D4 | 定义归档规则（`status: deprecated` + 超期移入归档目录） |
| G8 | **陪伴档案联动**：记忆库化会改 `profileWithDream` 的输入 | Telegram Companion 同步可能失效或丢内容 | D4 迁移清单 | 迁移时一并改 `syncProfile` 并实测 |
| G9 | **长笔记缺"上下文起点"**：几千行项目笔记里派发，祖先链可能过长 | 预算被无意义的上级占满 | D2 | 引入"作用域"：默认从最近一级标题开始，向上只取到预算为止 |
| G10 | **多库未定**：未来客户端可能管多个 vault | `ref` 的 `target` 少一个库标识维度 | D9 | `ref` 预留 `vault?` 字段，Obsidian 场景恒为空 |

其中 **G1 / G2 / G3 必须在写第一行注入代码之前处理**：G1 决定退路、G2 决定能不能发、G3 决定出问题时查不查得到。其余可以在对应阶段顺手做。
